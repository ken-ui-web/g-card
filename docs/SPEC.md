## 0. この文書の読み方（Codex への指示）

- **最初に「★ 開発の進め方」を読むこと。一度にすべてを実装してはいけない。** 段階ごとに作業を止め、オーナー（先生）のチェックを受けてから次へ進む。
- この文書は Gカードの**唯一の正式仕様**である。リポジトリでは `docs/SPEC.md` として配置して参照すること。
- この文書には完成形の仕様がすべて書かれているが、**実装するのは「今の段階」の範囲だけ**。ただし、後の段階で作り直しにならないよう、設計（データ構造・効果の部品化など）は完成形を見すえて行うこと。
- 【仮】が付いた数値・データは**暫定値**である。必ず「管理者画面」または「設定シート」から変更できるように実装し、コードに直書きしないこと。
- 【未決定】は今後オーナー（先生）が決める項目。仮データで動く状態にしておき、差し替えやすくすること。
- 仕様に書かれていない細部は、**中学生がiPadで迷わず使えること**を最優先に判断し、判断内容を `docs/DECISIONS.md` に記録すること。
- 文言はすべて日本語。生徒向けの文言は中学生が読める平易な表現にする（難しい漢字は避ける）。
- 外部アカウント作成・本番の鍵の発行など、Codex が実行できない作業は「27. セットアップ手順（人間が行う作業）」に記載している。

## ★ 開発の進め方（段階とオーナーチェック）【最重要】

### ★-1. 基本ルール
1. 開発は下の **段階1〜10** の順に進める。**1つの段階が終わったら必ず作業を止め、オーナーのチェックを受ける。**
2. オーナーから「OK」が出るまで、**次の段階の作業を始めない**。
3. 修正の指示が出たら、修正して再度チェックを受ける（OKが出るまで繰り返す）。
4. チェックの結果、ルールや数値が変わった場合は、この仕様書（`docs/SPEC.md`）を更新し、変更点を `docs/DECISIONS.md` に記録する。
5. 進み具合は `docs/PROGRESS.md` に記録する（どの段階が完了したか、チェックで出た指摘と対応）。
6. 作業中に大きな判断が必要な不明点が出たら、推測で大きく進めず、チェック時にまとめて質問する。小さな判断は自分で決めて `docs/DECISIONS.md` に記録する。

### ★-2. チェック時の報告のしかた
各段階の終わりに、次の形でオーナーに報告する（中学校の先生が読んでわかる、やさしい日本語で）。

```
【段階◯ 完了報告】
1. やったこと（箇条書き）
2. 確認のしかた（開くURL、iPadでの操作手順など）
3. チェックしてほしいポイント（チェックリスト形式）
4. 気になっている点・相談したいこと
5. OKが出たら次にやること
```

## 1. 概要

### 1-1. コンセプト
- 「Gカード」は**テストアプリ**であり、同時に**カードバトルゲーム**である。Gは「技術」のG。
- テストを解く・振り返りを提出する・ログインする・対戦する、などで **Gポイント** がたまる。
- Gポイントで **カード購入**（単品・ランダムパック）や **トレーニング**（筋トレ・走り込み）ができ、バトルを有利に進められる。
- バトルは**1対1の「じゃんけん」カードバトル**。勉強した生徒が有利になるが、じゃんけんで負ければダメージを与えられないため、**読み合い**が勝負を決める。
- 狙い：ゲームを楽しむために、何度もテストを解き、振り返りを書くようになること。

### 1-2. 種類（カードの属性）

| 種類 | 内部ID | イメージカラー | テーマ | 勝てる相手 |
|---|---|---|---|---|
| グー | `rock` | 黄色 | 肉弾戦 | チョキ |
| チョキ | `scissors` | 青 | 武器・道具による攻撃 | パー |
| パー | `paper` | 緑 | 特殊効果 | グー |

- **筋トレで育てられるのはグーのみ。** チョキは「買って手に入れる強さ」、パーは「戦略で流れを変える」役割。
- 世界観：技術（道具・機械・情報技術）の歴史をモチーフにしたカードを多く含める（例：げんのう、のこぎり、火縄銃、電動ドリル、レーザーカッター、ロボットアーム、プログラミング、AI）。

## 2. 用語

| 用語 | 意味 |
|---|---|
| Gポイント（G） | アプリ内通貨。現実のお金とは一切関係しない |
| カードマスタ | カードの種類ごとの定義（名前・種類・効果・画像など） |
| 所持カード | 生徒が持っているカード1枚1枚（**インスタンス**）。同じカードを複数枚持てる。筋トレ値は1枚ごとに持つ |
| デッキ | バトル開始時に選ぶ4枚（【仮】枚数は設定で3〜5に変更可） |
| 自分のカードセット | 自分の所持カードからデッキを組み、自分のライフ・筋トレ値で戦う方式（＝育成あり部門） |
| サンプルカードセット | 管理者が用意したカード群からデッキを組み、ライフ100・筋トレなしで戦う方式（＝実力勝負部門） |
| 最大ライフ | バトル開始時のライフ。初期100、走り込み1回で＋5 |
| 筋トレ値（trainLevel） | グーカード1枚ごとの強化回数。ダメージに加算される |

## 3. システム構成

### 3-1. 構成図

```
┌─ iPad（生徒）／PC（先生）────────────────────┐
│ Gカード Webアプリ（PWA）                              │
│ GitHub Pages で公開（画面・アニメーション・カード画像）  │
└──────┬──────────────────────┬──────────┘
       │ HTTPS（データ操作すべて）               │ オンライン対戦のみ
       ▼                                        ▼
┌─ Google Apps Script（Webアプリ）─┐   ┌─ Firebase（Sparkプラン・無料）─┐
│ ・ログイン検証・セッション発行       │   │ ・Realtime Database：対戦部屋の同期 │
│ ・採点／Gポイント／購入／ガチャ      │   │ ・Authentication：匿名ログイン      │
│ ・トレーニング／ミッション           │   │ ・個人情報は置かない（ニックネームのみ）│
│ ・管理者機能                        │   └──────────────────────┘
└──────┬─────────────────┘
       ▼
┌─ Googleスプレッドシート（学校のGoogleアカウント所有）┐
│ 生徒／所持カード／カードマスタ／テスト／回答／振り返り／   │
│ ポイント履歴／設定 など                                │
└───────────────────────────────┘
┌─ Googleドライブ ─┐  テスト問題の画像の保存先
└───────────────┘
```

### 3-2. 役割分担

| 担当 | 役割 |
|---|---|
| GitHub（リポジトリ・Pages・Actions） | フロントエンドのホスティング、カード画像などの静的アセット、自動デプロイ |
| GAS | **信頼できるサーバー役**。Gポイントの増減・採点・抽選は必ずここで行う |
| スプレッドシート | データベース。先生が直接閲覧できる |
| Firebase Realtime Database | オンライン対戦のリアルタイム同期のみ。対戦後は部屋データを削除 |
| Googleドライブ | テスト問題用画像（管理者がアップロード） |

### 3-3. 採用しないもの（理由）
- Firebase Blazeプラン／Cloud Functions／Cloud Storage：クレジットカード登録が不要な構成にするため使わない。
- Firestore：無料枠の1日あたり書き込み上限（20,000回）が対戦用途では不足する恐れがあるため、対戦は Realtime Database を使う。
- Supabase など外部DB：個人情報を学校のGoogleアカウント内にとどめるため使わない。

### 3-4. 重要な原則
1. **生徒の端末を信用しない。** Gポイント・所持カード・筋トレ値・ライフ・テストの正解はすべてGAS側で管理・計算する。
2. **テストの正解データは絶対に生徒の端末に送らない。**
3. GitHubリポジトリは公開される前提。秘密情報（正解、鍵、名簿）をリポジトリに置かない。
4. 学習から得るGポイントが収入の大部分（目安7割以上）になるよう、対戦報酬には1日の上限を設ける。

## 4. 認証・ユーザー

### 4-1. ログイン方式
- 学校のGoogleアカウント（Google Workspace for Education）でログインする。
- フロントで **Google Identity Services（GIS）** によりIDトークンを取得し、GASの `login` に送る。
- GASは以下を検証する：
  - 署名・有効期限（`https://oauth2.googleapis.com/tokeninfo?id_token=` で検証してよい）
  - `aud` が自アプリのOAuthクライアントIDと一致
  - `hd`（ドメイン）が設定 `schoolDomain` と一致、`email_verified` が true
  - メールアドレスが「生徒名簿」または「管理者リスト」に存在する
- 検証に成功したら、GASは**独自のセッショントークン**を発行する。
  - 内容：`{email, role, exp}` をHMAC-SHA256で署名（鍵はスクリプトプロパティ `SESSION_SECRET`）
  - 有効期限：【仮】7日（設定 `sessionDays`）
  - フロントは localStorage に保存し、以降のAPI呼び出しはこのトークンを使う（GISのトークン期限1時間に左右されないようにするため）。
- 名簿にないアカウントは「このアカウントは登録されていません。先生に伝えてください」と表示してログイン不可。

### 4-2. iPad のホーム画面アプリ（スタンドアロン）でのログイン【要検証】
- iOS のホーム画面から起動したPWAでは、ポップアップ方式のGoogleログインが正常に戻らない場合がある。

## 6. バトル仕様

### 6-1. 基本ルール（確定）
- 1対1。各プレイヤーはデッキ **4枚**（設定 `deckSize`、3〜5）を選ぶ。
- 両者が選び終えると、**互いのカードの裏面が表示される**。裏面には種類（グー／チョキ／パー）が色とアイコンで表示されるため、**相手の手の種類はわかる**が、カードの中身（名前・効果）はわからない。
- 自分のカードは、各カードの下に詳細（名前・効果・ダメージ値・筋トレ値）が表示される。
- 各ラウンドで、残っているカードから1枚を選ぶ。両者が選ぶと公開され、じゃんけんで勝敗を決める。
- **勝った側のカードの効果だけが発動する。** あいこの場合はカードを表にするが、どちらの効果も発動しない。
- 使ったカードは捨て札になる（再使用不可）。
- 最終ラウンドは残り1枚のため**自動選択**とし、両者が「オープン！」ボタンを押したら公開する（勝敗は予想できるが、中身の公開を演出として楽しむ）。読み合いの中心は最終ラウンドより前のラウンド。
- 終了条件：
  - いずれかのライフが0以下になった時点でそのプレイヤーの敗北（判定タイミングは6-5参照）。
  - 両者同時に0以下になった場合は引き分け。
  - 全ラウンド終了時、**残りライフが多いほうの勝利**。同じなら引き分け。
- 回復で最大ライフを超えることはない。

### 6-2. カードセットとライフ

| カードセット | デッキの選び方 | 最大ライフ | 筋トレ値 |
|---|---|---|---|
| 自分のカードセット | 自分の所持カード（インスタンス）から4枚。同じカードを複数持っていれば複数枚入れてよい。全部同じ種類でもよい | 100＋走り込み回数×5 | 有効 |
| サンプルカードセット | 管理者が指定したサンプルカード群から4枚 | 100（設定 `initialLife`） | 無効（0扱い） |

- 1枚の所持カードを同じデッキに2回入れることはできない（所持している枚数まで入れられる）。
- デッキ選択画面では、前回使ったデッキを初期選択状態にする。
- 同じカードを複数持つ場合は「パンチ（ダメージ25・💪+5）」「パンチ（ダメージ20）」のように、どの1枚かを区別できる表示にする。

### 6-3. バトルの流れ（画面遷移）

1. **デッキ選択**（S10）：所持カード（またはサンプルカード群）から4枚を選んで「決定」。オンラインでは制限時間90秒（時間切れはランダムに補完）。
2. **対戦準備画面**（S11）：
   - 上段：相手の4枚の裏面（種類の色とアイコン）と相手のライフバー。
   - 下段：自分の4枚（裏面風の枠に種類色）＋各カードの下に詳細、自分のライフバー。
3. **ラウンド選択**：自分のカードをタップして選び「決定」。相手の待機中は「相手が選んでいます…」を表示。オンラインは制限時間30秒（時間切れはランダム）。
4. **公開画面**（画面が切り替わる）：
   - 両者がカードを決めた後、ラウンド番号をアニメーションで表示し、カードを隠したまま「VS」の緊張感を作ってからカードを出す。
   - 互いが選んだカードの裏面が中央で向かい合って表示される。
   - カードの種類とじゃんけんの勝敗を明確に表示する。感情的なリアクション文は表示しない。裏面は見終わるまで保持する。
   - カードが表に裏返るアニメーション（3D回転）。
   - 勝った側の効果が発動する演出（ダメージ数値のポップ、ライフバーの減少、画面の揺れなど）。
   - 効果に対象選択がある場合（例：手品）、**勝った側**が選ぶUIを表示する（オンラインは制限時間20秒、時間切れはランダム）。
   - ラウンド終了時の継続効果（毒・回復など）を処理して表示する。
5. 次のラウンドへ（準備画面に戻り、使ったカードは消えている）。
6. 全ラウンド終了、またはライフ0で **バトル結果**（S12）へ。勝敗、残りライフ、獲得Gポイント、ミッションの進み具合を表示する。

### 6-4. じゃんけん判定
- `rock` > `scissors`、`scissors` > `paper`、`paper` > `rock`。
- 判定には**その時点の種類**（効果で変化していればその種類）を使う。

### 6-5. ラウンドの解決順序（実装の正）

```
1. 選択確定
   - 「プログラミング」で出すカードを指定されていれば、そのカードを強制選択。
   - 「目隠し（ジャイアントスイング）」状態のプレイヤーは、残りカードからランダムに選ばれる。
2. 公開・じゃんけん判定
3. 敗北→あいこ変換
   - 負けたプレイヤーに「AI」の効果（次のラウンドで負けたらあいこ扱い）が付いていれば、あいこにする。効果は消費。
4. 勝者のカード効果を、カードに定義された順に解決
   - 「効果なし（封印・ベアハッグ）」状態のカードが勝った場合、効果は発動しない（じゃんけんの勝ちのみ）。
   - あいこの場合、どちらの効果も発動しない。
5. 前のラウンドから持ち越した「勝敗に応じた効果」（例：ブーメランの「負けても10ダメージ」）を処理
6. KO判定（両者0以下→引き分け、片方0以下→そのプレイヤーの敗北）
7. ラウンド終了時効果（時間差ダメージ、毒、太陽光パネルの回復）を処理（あいこのラウンドでも処理する）
8. KO判定
9. 「次のラウンドのみ」有効な効果の期限を進める
10. 最終ラウンドだった場合、ライフを比較して勝敗を決定
```

### 6-6. ダメージ計算

1つのダメージ（1ヒット）について：

```
① 基本値 ＋ 筋トレ値 × 筋トレ倍率（グーカードのみ。サンプルカードセットでは0）
② × 倍率系の補正（応援団×2、気合いため×2 など。複数あれば掛け合わせ）
③ ＋ 加算系の補正（張り手−5、タックル−10 など）
④ 0未満なら0
⑤ 相手のシールドを適用（貫通効果があれば無視）
⑥ 相手のライフを減らす
```

- 複数ヒット（例：連続パンチ 10×3）は、**1ヒットごとに①〜⑥を計算する**（筋トレ値・補正もヒットごとにかかる）。
- シールド（バリア／ファイアウォール／鏡）は**相手から受ける次の1ヒット**に適用され、そこで消費される。時間差ダメージや毒にも適用される。
  - バリア：半分（端数切り捨て）
  - ファイアウォール：0
  - 鏡：そのヒットのダメージを、自分ではなく攻撃した側が受ける（跳ね返したダメージはさらに跳ね返らない）
  - シールドが複数ある場合は、付与された順に1つだけ使う。
- 自分へのダメージ（反動）にはシールドも補正もかからない。
- 回復は最大ライフまで。

### 6-7. 状態の持ち方（エンジン設計の指針）
- バトルエンジンは**副作用のない純粋なTypeScriptモジュール**として実装し、CPU戦・この端末で対戦・オンライン対戦の3つで共通利用する。
- 乱数（百裂拳、ランダム補完など）は**シード付き乱数**を使う（オンラインでは両端末が同じ結果になるようにするため）。
- プレイヤーの状態の例：

```ts
type PlayerState = {
  life: number; maxLife: number;
  hand: BattleCard[];          // 残りカード
  used: BattleCard[];          // 使用済み
  shields: Shield[];           // 'half' | 'zero' | 'reflect'
  modifiers: Modifier[];       // 次のラウンド用の補正（倍率・加算・種類条件）
  timedEffects: TimedEffect[]; // 時間差ダメージ・毒・回復
  flags: { tieOnNextLoss?: boolean; forcedCardId?: string; blind?: boolean;
           canSeeOpponentDetails?: boolean; retaliateNextRound?: number };
};
type BattleCard = {
  instanceId: string; cardId: string;
  originalType: CardType; currentType: CardType;
  trainLevel: number; nullified: boolean;
};
```

- 種類が効果で変わったカードには「手品で【グー】に変化」のような表示を付け、裏面の色もアニメーションで変える。

### 7-2. レア度と枠

| レア度 | 枠デザイン | 入手 |
|---|---|---|
| N（ノーマル） | 種類色の単色枠 | ショップ・パック |
| R（レア） | 銀色のメタリック枠 | ショップ・パック |
| SR（スーパーレア） | 金色の枠＋光が流れるアニメーション | 一部ショップ・パック |

- 台紙・枠の違いは表面の完成画像へ組み込む（7-5、23章）。SR・URの「光が流れる」「キラキラ」の動きは、完成画像の上にCSSアニメーションを重ねて表現する。
- 名前・種類を示すアイコン・効果文は表面画像に焼き込む。レア度や「グー」の文字は表記しない。動的に重ねる文字は右上の最終ダメージだけ（7-5）。

### 7-3. 効果プリミティブ（effects JSON）

カード効果は以下の部品の組み合わせで表現し、管理者画面のカード登録でも同じ部品を選んで作れるようにする。

| type | パラメータ | 内容 |
|---|---|---|
| `damage` | `amount`, `hits`(=1), `pierce`(=false) | ダメージ。`pierce` はシールド無視 |
| `randomDamage` | `min`, `max` | ランダムダメージ（シード乱数） |
| `damageFromLostLife` | `ratio` | 自分が失ったライフ（最大−現在）×ratio のダメージ（切り捨て） |
| `damagePerOpponentRemaining` | `per` | 相手の残りカード枚数×per のダメージ |
| `trainingScaledDamage` | `base`, `perTraining` | base＋このカードの筋トレ値×perTraining（この場合①の筋トレ加算はしない） |
| `selfDamage` | `amount` | 自分へのダメージ（反動） |
| `heal` | `amount` | 回復 |
| `drain` | `amount` | ダメージを与え、実際に与えた量だけ回復 |
| `changeOpponentType` | `to`, `count`(=1) | 相手の残りカードを選んで種類を変える |
| `changeAllOpponentType` | `to` | 相手の残りカードをすべて変える |
| `changeOwnType` | `count`(=1) | 自分の残りカードを選び、好きな種類に変える |
| `shield` | `mode`: `half`/`zero`/`reflect` | 次に受けるダメージへのシールド |
| `nullifyOpponentCard` | `count`(=1) | 相手の残りカードを選び「効果なし」にする |
| `revealOpponent` | なし | 以降、相手の残りカードの詳細が見える |
| `blindOpponent` | なし | 相手は以降、自分の残りカードが裏向き・シャッフルされ、ランダムに出すことになる |
| `nextRoundModifier` | `target`: `self`/`opponent`, `multiplier`, `add`, `typeFilter` | 次のラウンドで出すカードのダメージ補正 |
| `delayedDamage` | `amount`, `afterRounds`(=1) | 指定ラウンド後の終了時にダメージ |
| `poison` | `amount` | このラウンドの終了時から、毎ラウンド終了時にダメージ |
| `regen` | `amount` | このラウンドの終了時から、毎ラウンド終了時に回復 |
| `retaliateNextRound` | `amount` | 次のラウンドで自分が負けても、相手にこのダメージ |
| `forceOpponentNext` | なし | 相手の残りカードから1枚を選び、次のラウンドで出させる |
| `swapCards` | なし | 自分の残りカード1枚と相手の残りカード1枚を交換（筋トレ値もカードと一緒に移る） |
| `tieOnNextLoss` | なし | 次のラウンドで自分が負けたら、あいこ扱いにする |

- 「選ぶ」効果は**勝った側**が対象を選ぶ。相手のカードは種類（と見えていれば詳細）しかわからない状態で、位置で選ぶ。
- 対象がない場合（最終ラウンドなど）は「効果の対象がありません」と表示して何もしない。

### 7-4. 筋トレ（グーのみ）
- 筋トレはグーカード1枚（インスタンス）ごと。1回で**ダメージ＋1**。
- 2枚目の同じカードは筋トレ値0から育てる。
- カード上の筋トレ欄には動的な「+5」を表示する。基本攻撃力（例：20）は表面画像に含める。バトル時の実ダメージは基本攻撃力に筋トレ値を加えた値として計算する。
- `trainingMultiplier` が2のカード（伝説の拳）は、筋トレ1回で＋2になる。

### 7-5. カードの見た目（表面レイアウト・縦3:4）

#### 表面の作り方（2026-10-03のB案採用で変更）

- 表面はカードごとに縦3:4の**完成画像1枚**を使う。採用したB案では、男の子のイラスト、台紙、枠、種類を示すこぶしアイコン、カード名「パンチ」、効果文「20のダメージを与える」を一体として画像生成する。制作段階でも別々の素材を枠へ合成しない。
- レア度・種類名・筋トレの独立したラベルと筋トレ専用のバッジは画像に入れない。効果文に含まれる「【グー】」などの種類名は、効果を正しく伝えるため画像に含める。ダメージ効果のあるカードは右上の円を空欄にする。
- ブラウザで表面に別画像を重ねない。**画面が描く文字は右上の最終ダメージ（基本ダメージ＋筋トレ加算、例：`25`）だけ**。筋トレ加算値を単独で表示しない。ダメージ効果のないカードは数値を重ねず、右上の円は画像内の装飾にできる。
- 完成画像を目視して名前と効果文を確認する。
- 種類色はグー黄／チョキ青／パー緑、レア度の表現はN単色／R銀／SR金／URホロの方針を保つ。SR・URの光の演出はCSSで追加できる。
- カード名や効果文が管理者設定で変わるときは、対応する完成画像も再生成・再公開する。これは文字を画像へ固定する方式の運用上の条件である。

### 7-6. カードの裏面
- 3種類：グー（黄）、チョキ（青）、パー（緑）。中央に手のアイコン（グー＝握りこぶし、チョキ＝ピースの手、パー＝開いた手のひら）と、Gのエンブレム。
- 色だけでなく**アイコンで区別できる**こと（色覚の多様性に配慮）。
- **画像生成で作る**（23-5）。1枚の完成した画像として作り、文字は入れない（Gのエンブレムは図形として描く）。
- 効果で種類が変わったとき（手品など）は、裏面の画像を切り替えるアニメーションで表現する。

## 10. CPUの思考（3段階）

CPUは**ズルをしない**（プレイヤーがそのラウンドに選んだカード、見えていない詳細は参照しない）。CPUが使えるのは、プレイヤーにも見えている情報（相手の裏面の種類・残り枚数・ライフ・使用済みカード）と自分の手札だけ。

| レベル | カード選択 | 効果の対象選択 |
|---|---|---|
| Lv1 | 残りカードからランダム | ランダム |
| Lv2 | 相手の残りカードの種類を数え、勝てる相手が最も多いカードを選ぶ（70%）。30%はランダム | 自分の残りカードで勝てる種類に変える、など単純な最善手 |
| Lv3 | 相手の残りカードがそれぞれ等確率で出ると仮定し、全組み合わせを先読みして、最終的なライフ差の期待値が最大になるカードを選ぶ。最終ラウンドの確定結果や、自分の継続効果も考慮する | 先読みで最も期待値が上がる対象を選ぶ |

- CPUは選択時に0.8〜1.5秒の「考え中」演出を入れる。

## 11. 対戦モード

### 11-1. モードとカードセットの組み合わせ

| モード | 自分のカードセット | サンプルカードセット | 報酬 |
|---|---|---|---|
| オンライン対戦（生徒同士） | ○ | ○ | あり |
| CPU対戦（Lv1〜3） | ○ | ○ | あり |
| この端末で対戦（2人） | ✕ | ○（両者とも） | なし |

- 流れ：対戦する → モード選択 → カードセット選択（この端末で対戦はサンプル固定） → CPUならレベル選択／オンラインならマッチング → デッキ選択 → バトル。

### 11-2. この端末で対戦（ローカル2人）
- 最初にプレイヤー名（任意、未入力なら「プレイヤー1」「プレイヤー2」）を入力。
- 選択のたびに目隠し画面をはさむ：「プレイヤー1の番です。プレイヤー2は見ないでね」→ 選択 →「プレイヤー2に渡してください」→ …
- 共通の盤面では裏面だけを表示し、自分のカードの詳細は自分の番のときだけ表示する。
- 公開画面は両者で一緒に見る。
- Gポイント・ミッション・ランキングには影響しない。

### 11-3. CPU対戦
- バトルはすべて端末内で処理する。
- 終了時にGASの `reportBattle` で結果を送り、報酬を受け取る（1日の上限あり）。

### 11-4. オンライン対戦
- 部門：「自分のカードセット」と「サンプルカードセット」は**別々にマッチング**する（混ざらない）。
- マッチング方法：
  - **ランダムマッチ**：同じ部門で待っている相手と自動で組む。
  - **ルームコード**：部屋を作ると4桁のコードが出る。友達がコードを入力して参加。
- 相手の表示：ニックネームのみ。
- 制限時間：デッキ選択90秒、ラウンド選択30秒、効果の対象選択20秒（時間切れはシード乱数でランダムに決定）。
- 切断：相手の接続が30秒以上切れたら不戦勝。30秒以内なら再接続して続きから。
- 詳細設計は20章。

| テスト満点ボーナス | ＋50 | そのテストで初めて満点を取ったときのみ |
| テストの受け直し | 自己ベストを上回った分の差額のみ | 例：前回60G分 → 今回80G分 なら＋20G |
| 振り返り提出 | 20（お題ごとに設定可） | お題ごとに1回 |
| デイリーミッション | 各10〜30 | 13章 |
| ウィークリーミッション | 各100 | 13章 |
| CPU対戦 勝利 | Lv1：5／Lv2：10／Lv3：20 | 報酬が出るのは1日3回まで（`cpuRewardDailyCap`） |
| オンライン対戦 | 勝利10／引き分け5／敗北3 | 報酬が出るのは1日3回まで（`onlineRewardDailyCap`） |
| 本日の初勝利 | ＋20 | CPU・オンライン問わず1日1回 |
| この端末で対戦 | 0 | ― |

- 上限を超えた対戦も遊べる（報酬が0になるだけ）。結果画面に「今日の報酬はあと◯回」と表示する。

### 12-2. 消費

| 用途 | 価格 |
|---|---|
| ショップ（単品） | N：50／R：150／SR：400（カードマスタの `shopPrice`） |
| ノーマルパック | 200G・3枚入り |
| 筋トレ（1回） | `20 ＋ 2 × そのカードの現在の筋トレ値`（1回目20G、10回目38G…） |
| 走り込み（1回） | `60 ＋ 6 × これまでの走り込み回数`（ライフ＋5） |

### 12-3. パック（ランダム）
- 1パック3枚。1枚ごとにレア度を抽選し、そのレア度のカードからランダムに選ぶ（パック対象カードのみ）。
- 排出率【仮】：N 60%／R 30%／SR 8.5%／UR 1.5%。**排出率はパック購入画面に必ず表示する。**
- **天井**：SR以上が出ないまま10パック開けたら、次のパックの1枚目はSR以上が確定。SR以上が出たらカウントはリセット。残りの回数を画面に表示する（「あと3パックでSR以上確定！」）。
- 1日の購入上限：10パック（`packDailyLimit`）。
- 抽選は必ずGASで行う。
- 開封演出：パックが破れる → カードが1枚ずつ裏返る。SRは金色、URは虹色に光る特別演出。この演出の間にGASの応答を待つ（待ち時間を感じさせない）。
- パックは複数種類を作れる（期間限定パックなど）。パックごとに収録カード・排出率・価格・販売期間を設定できる。

### 12-4. 売却（ダブりの還元）
- 所持カードを売ってGポイントに戻せる：N 10／R 30／SR 100／UR 300【仮】。
- 筋トレしたカードを売るときは「筋トレの成果も消えます」と確認する。
- 所持カードがデッキ枚数（4枚）未満になる売却はできない。

### 12-5. トレーニング画面（S15）
- **筋トレ**：所持しているグーカードの一覧から1枚を選ぶ → 「筋トレする」ボタン。押すたびにキャラクターが筋トレするアニメーションとともに、ダメージ表示が＋1される。
- **走り込み**：「走り込む」ボタン。押すたびに最大ライフ＋5。
- 連打に対応する：押した瞬間に表示上の数値とGポイントを更新し、0.8秒間操作がなければまとめてGASに送信する（`train` APIはまとめて処理）。GASの結果と表示がずれた場合はGASの値に合わせる。
- 次の1回に必要なGポイントを常に表示する。

### 12-6. バランスについての注意（オーナー向け）
- 走り込み（ライフ＋5）は毎回のバトルで必ず効くのに対し、筋トレ（＋1）はそのカードで勝ったときしか効かない。そのため、走り込みの費用を高めに設定している。
- 実際に遊んでみて、`runCostBase` などの設定や、必要なら `maxLifeCap`（最大ライフの上限。空欄なら無制限）で調整する。
- 公平な実力勝負の場として「サンプルカードセット」部門を用意している。

## 14. テスト機能（Googleフォームのテスト機能を参考）

### 14-1. 問題の形式

| 形式 | 採点 | 備考 |
|---|---|---|
| ラジオボタン（択一） | 自動 | |
| チェックボックス（複数選択） | 自動 | 正解の組み合わせと完全一致で得点 |
| プルダウン | 自動 | |
| 記述式（短文） | 自動 | 正解を複数登録可。前後の空白除去、全角・半角の統一、大文字・小文字を区別しないオプション |
| 段落（長文） | 手動 | 配点0なら採点なし。配点ありなら管理者が手動採点 |
| 均等目盛（1〜5など） | なし | アンケート用 |
| 選択式グリッド | 自動 | 全行正解で得点 |
| チェックボックスグリッド | 自動 | 全行正解で得点 |

### 14-2. 問題ごとの設定
- 問題文、画像（任意）、選択肢、正解、配点、必須／任意
- 正解時のフィードバック、不正解時のフィードバック（解説）
- 選択肢の順番をシャッフル

### 14-3. テストごとの設定
- タイトル、説明
- セクション（ページ）分け。セクションごとにタイトル・説明
- 問題の順番をシャッフル（セクション内）
- 公開／非公開、受験期間（開始・終了日時）
- 対象クラス（複数選択可、全クラスも可）
- 受験回数：無制限／1回／N回
- 結果の表示：送信後すぐ／管理者が公開したら
- 表示内容：得点のみ／得点＋正誤／得点＋正誤＋正解＋フィードバック
- Gポイント倍率（初期1）

### 14-4. 生徒の受験画面（S04〜S06）
- テスト一覧：タイトル、期限、状態（未受験／受験済み・ベスト◯点／期限切れ）。
- 受験画面：1セクション＝1ページ。上部に進み具合のバー。「次へ」「戻る」。必須問題が未回答なら先に進めない。
- 送信前に確認ダイアログを表示。
- 送信後：「採点中…」の演出 → 得点表示 → 獲得Gポイントがコインになって飛んでくる演出 → 設定に応じて問題ごとのフィードバックを表示。
- 回答途中のデータは端末内に一時保存し、アプリを閉じても再開できる（送信前のみ）。

### 14-5. 採点とGポイント
- 採点はGASで行う。**正解データ（answerKey）はAPIのレスポンスに一切含めない。**
- 獲得G＝`round(得点 ÷ 満点 × 100 × テスト倍率)`。
- 受け直し：今回の獲得G相当値が自己ベストを上回った場合、その差額のみ付与。
- 満点ボーナスは初回の満点時のみ。
- 段落問題を手動採点した場合、採点確定時に合計点を再計算し、ベストが上がれば差額を付与する。

## 19. GAS API

### 19-1. 共通仕様
- GASを「ウェブアプリ」としてデプロイ（実行ユーザー：自分＝先生、アクセス：全員）。本人確認はセッショントークンで行う。
- フロントからは `POST`、`Content-Type: text/plain;charset=utf-8`（CORSのプリフライトを避けるため）、本文はJSON。

```json
// リクエスト
{ "action": "buyCard", "session": "<token>", "requestId": "<uuid>", "payload": { ... } }
// レスポンス
{ "ok": true, "data": { ... } }
{ "ok": false, "error": { "code": "NOT_ENOUGH_POINTS", "message": "Gポイントが足りません" } }
```

- **Gポイントや所持カードを変更するAPIは `requestId` で二重実行を防ぐ**（同じrequestIdは前回の結果を返す。CacheServiceで6時間保持）。
- 書き込みは `LockService.getScriptLock()` で排他制御する。
- 変更系APIのレスポンスには、最新の `gPoint` と変更された所持カードを含める（フロントの表示を正しい値に合わせるため）。
- 混雑などで失敗したら、フロントは同じrequestIdで最大3回まで自動再送する。
- カードマスタ・設定・ミッション定義は CacheService にキャッシュする（管理者が変更したらキャッシュを消す）。
- スクリプトのタイムゾーンは `Asia/Tokyo`。

### 19-2. 生徒向けAPI

| action | 内容 |
|---|---|
| `login` | IDトークンを検証してセッションを発行。初回なら `needsNickname: true` |
| `setNickname` | ニックネーム設定（初回は初期カード・ウェルカムボーナスも付与） |
| `bootstrap` | 起動時に1回呼ぶ。ログインボーナス処理＋プロフィール、G、最大ライフ、所持カード、前回デッキ、カードマスタ、パック、公開設定、ミッション進行、未受験テスト数・未提出振り返り数をまとめて返す |
| `listTests` | 受験できるテスト一覧と自分の状態 |
| `getTest` | 問題（正解・フィードバックを除く）。シャッフルはここで行う |
| `submitTest` | 採点・G付与・ミッション進行。結果表示設定に応じて正誤・フィードバックを返す |
| `getTestResult` | 「管理者が公開したら」設定のテストの結果を後で見る |
| `listReflections` / `submitReflection` | 振り返りお題の一覧／提出 |
| `buyCard` | ショップで購入 |
| `openPack` | パックを購入・抽選（天井・1日上限を処理） |
| `sellCard` | 売却 |
| `train` | `{ items: [{kind:"muscle", ownedId, count}, {kind:"run", count}] }` をまとめて処理。払える回数まで実行し、結果を返す |
| `saveDeck` | 前回デッキを保存 |
| `getBattleConfig` | サンプルカードセット・CPUデッキの内容 |
| `reportBattle` | `{battleId, mode, deckMode, cpuLevel, result, opponentNickname}`。同じ `battleId`＋email は1回のみ。1日上限を適用して報酬を付与 |
| `getRanking` | 週間ランキング |
| `getImage` | テスト画像（base64） |

### 19-3. 管理者向けAPI
`admin*` の名前で用意し、すべて管理者権限を確認する：`adminDashboard`, `adminImportRoster`, `adminListUsers`, `adminAdjustPoints`, `adminResetNickname`, `adminGetUserCards`, `adminSaveTest`, `adminDeleteTest`, `adminDuplicateTest`, `adminGetResponses`, `adminGradeResponse`, `adminPublishResults`, `adminSaveReflection`, `adminGetReflectionResponses`, `adminSaveCard`, `adminSavePack`, `adminSaveDeck`, `adminSaveMission`, `adminSaveSettings`, `adminExportCsv`, `adminUploadImage`。

### 19-4. 性能の注意
- GASの1回の応答は0.5〜2秒かかる前提で設計する。画面遷移のたびにAPIを呼ばず、`bootstrap` で取得したデータを端末内で使い回す。
- 同時実行数に上限があるため、1クラス（約33名）が一斉にテストを送信しても処理できるように、`submitTest` の処理は短く保つ（必要な行だけを読む、まとめて書き込む）。

## 20. オンライン対戦の設計（Firebase Realtime Database）

### 20-1. 方針
- Firebaseの **Authentication（匿名ログイン）** と **Realtime Database** のみを使う（Sparkプラン）。
- Sparkプランの同時接続上限は100。**オンライン対戦画面にいる間だけ接続**し、それ以外は `goOffline()` する。上限に達した場合は「混雑しています。少し待ってからもう一度試してね」と表示。
- データベースに保存するのは、ニックネーム・対戦の進行に必要な情報だけ。氏名やメールアドレスは保存しない。
- 対戦終了後、部屋データは削除する（`expiresAt` を持たせ、古い部屋は次回接続時にも掃除する）。

### 20-2. データ構造（例）

```
/queue/{deckMode}/{uid}      : { nickname, maxLife, joinedAt }
/rooms/{roomId}
   meta    : { code, deckMode, deckSize, seed, status, hostUid, createdAt, expiresAt }
   players : { {uid}: { nickname, maxLife, connected, lastSeen } }
   decks   : { {uid}: { types: ["rock", ...], commit: "<sha256>" } }
   rounds  : { {n}: {
                 commit : { {uid}: "<sha256(index + salt)>" },
                 reveal : { {uid}: { index, salt, card: {cardId, trainLevel, ...} } },
                 choices: { {uid}: { ... 効果の対象選択 ... } },
                 stateHash: { {uid}: "<解決後の状態のハッシュ>" } } }
   final   : { {uid}: { deck: [...], salt } }
```

### 20-3. 選択を相手に見られないための仕組み（コミット・リビール方式）
1. デッキ確定時、各自は「種類の並び」と「デッキ全体のハッシュ（commit）」だけを書き込む。中身は書かない。
2. 各ラウンドで、まず「選んだカード番号＋ランダムな文字列」のハッシュだけを書き込む。
3. 両者のハッシュがそろったら、それぞれが番号・ランダム文字列・カードの中身を公開（reveal）する。相手側はハッシュと一致するか確認する。
4. 両端末が同じバトルエンジン・同じシードで解決し、状態ハッシュを書き込んで一致を確認する。一致しない場合は「無効試合」にする。
5. のぞき見など、相手の詳細が必要な効果が発動した場合は、相手側の端末が自動で該当カードの中身を公開する。
6. 終了時に両者がデッキ全体を公開し、最初のハッシュと照合する。不一致は `reportBattle` に `suspicious: true` を付けて送る（管理者画面で確認できるように）。

### 20-4. セキュリティルール（方針）
- `rooms/{roomId}` は、その部屋の参加者の `uid` だけが読み書きできる。
- 各プレイヤーは自分の `uid` の場所にだけ書き込める。
- `queue` は自分のエントリのみ書き込み可。マッチングはトランザクションで行う。

### 20-5. 切断の処理
- `onDisconnect()` で `connected: false` と `lastSeen` を記録する。
- 相手が30秒以上切断したら、残った側の勝ち（不戦勝）。

## 23. 画像生成の指示（Codex向け）

### 23-0. 生成の進め方（必ず守る）
1. **段階1：パンチ（G001）の男の子イラストを共通に使い、表面の完成画像を3案**作る。グーの裏面は採用済み。3案をオーナーのチェックに出す。
2. OKが出たら、そのプロンプトとスタイルを「確定版」として `docs/IMAGE_STYLE.md` に記録する。NGなら作り直して再チェック。
3. **段階2：キック・火縄銃・手品の表面完成画像**と、チョキ・パーの裏面を確定版のスタイルで生成し、チェックを受ける。
4. **段階4：追加カードの表面完成画像**は、確定版のスタイルで5枚程度ずつ生成し、そのたびにチェックを受ける。SR・URの表面は初めて必要になったときに1枚ずつ生成してチェックを受ける。
5. **段階5：ロゴ**を1枚生成してチェック → OKならアプリアイコン・コイン・メニューアイコンなどを生成。
6. **段階10：背景・パック・CPUキャラなど**も、まず1枚をサンプルとして生成してチェックを受けてから、残りを生成する。
7. オーナーのOKなしに、まとめて大量に生成しない。
8. 下のプロンプトは**たたき台**。チェックの結果で変わった場合は、確定版を優先する。

### 23-1. 方針
- **見た目の質を最優先する。** カードの表面完成画像・裏面・ロゴ・アプリアイコン・Gポイントのコイン・メニューアイコンを画像で作る（23-5）。カード表面は枠・人物・アイコン・文字をまとめて一体の画像として生成し、アプリでも完成画像1枚を表示する。
- **カード表面は例外として文字を画像に含める。** カード名と効果文、種類を示すアイコンを画像に組み込む。レア度・種類名・筋トレの表記は入れず、右上の最終ダメージのみ画面で重ねる。ボタンや画面の見出し・本文はアプリの文字で表示する。
- すべての画像で、色づかい・光の当たり方・線の太さ・質感をそろえ、1つのゲームとして統一感を出す。
- 学校で使うため、**血・流血・残酷な表現・実在の人物・実在のキャラクター・ブランドは禁止**。武器は「物」として迫力ある見せ方にし、人に向けている構図にしない。攻撃の相手が必要な場合は「トレーニング用ダミー人形」か「ロボット」にする。
- 人物は中学生くらいの元気なキャラクター（運動着）。**パンチG001は男の子**。他のカードも絵柄をそろえる。
- 出力：PNGで生成 → WebPに変換（品質80程度）。カードイラストは **768×1024（縦3:4）**。
- 表面完成画像の保存先とファイル名：`public/images/cards/{cardId}-front.webp`（段階1の3案は `G001-front-a/b/c.webp`）。制作素材は `design-source/` に保存する。

| Gポイントの改ざん | 増減はすべてGASで計算。フロントの値は表示用 |
| テストの正解の流出 | 正解はスプレッドシートとGASの中だけ。APIで返さない |
| 二重送信による二重付与 | requestIdで二重実行を防ぐ |
| 対戦結果の偽装 | CPU・オンラインとも報酬に1日の上限。同じ対戦IDは1回のみ。オンラインはコミット・リビールで不正を検出して記録 |
| 名簿外の利用 | ドメインと名簿の両方で確認 |
| 管理者機能の不正利用 | GAS側で毎回、管理者メールアドレスか確認 |
| 個人情報 | 個人情報はスプレッドシート（学校のGoogleアカウント）のみ。Firebaseにはニックネームだけ。GitHubには個人情報を置かない |
| 不適切なニックネーム | 簡易NGワードチェック＋管理者によるリセット |

## 27. セットアップ手順（人間が行う作業）

Codex は以下の手順書を `docs/SETUP.md` として、画面のスクリーンショットがなくても進められる丁寧さで作成すること。**手順は、必要になる段階の直前に書き足し、オーナーに依頼する**（最初から全部をお願いしない）。

| 手順 | 必要になる段階 |
|---|---|
| 1 | 段階1 |
| 2、3、6、7、8、9 | 段階5 |
| 4 | 段階9 |
| 5 | 段階5（GASのURL・クライアントID）／段階9（Firebaseの設定値） |

1. **GitHub**：リポジトリを作成し、Pagesを「GitHub Actions」で有効化。
2. **Google Cloud**（学校のGoogleアカウント）：プロジェクト作成 → OAuth同意画面（内部）→ OAuthクライアントID（ウェブアプリ）を作成し、承認済みのJavaScript生成元にGitHub PagesのURLを登録。
3. **スプレッドシートとGAS**（学校のGoogleアカウント）：スプレッドシートを作成 → Apps Script を開いて `gas/` のコードを貼り付け（または clasp）→ スクリプトプロパティに `SESSION_SECRET`、`GOOGLE_CLIENT_ID` を設定 → `setup()` を実行 → ウェブアプリとしてデプロイし、URLを控える。
4. **Firebase**：プロジェクト作成（Sparkプランのまま）→ 匿名ログインを有効化 → Realtime Database を作成し、セキュリティルールを貼り付け → ウェブアプリの設定値を控える。
5. **GitHub Actions の変数**に `VITE_GAS_URL`、`VITE_GOOGLE_CLIENT_ID`、`VITE_FIREBASE_CONFIG` を登録。
6. **Settings シート**に `schoolDomain`、`adminEmails` を入力。
7. 管理者画面から**名簿CSVをインポート**。
8. 学校のGoogle Workspace管理者に、アプリ（OAuthクライアント）を生徒が使えるよう許可してもらう（許可済みとのこと）。
9. iPadでURLを開き、共有ボタン →「ホーム画面に追加」。
